    Field guide/Chapter 01

    Timing & duration

    Before you choose a curve, choose how long. Duration is the loudest control in motion design: the same movement reads as instant, confident or lazy depending on nothing else. This chapter is about picking that number on purpose.

    • Scale time with distance so speed feels consistent
    • Give entrances and exits different timing
    • Meet the 100ms feedback deadline even when work is slow

      Duration sets the mood

      The six balls below travel the same distance on the same curve. Only the duration changes, and each row has a different personality.

      People perceive anything under roughly 100ms as instantaneous and anything over about a second as a wait. Most interface motion lives between those limits: 150–250ms for small components such as toggles and chips, 250–400ms for dropdowns and cards, and up to about 500ms for large surfaces like modals and drawers.

      Past half a second, motion starts to perform for you rather than work for you. That is fine for a rare hero moment and tiring for something you trigger fifty times a day. Frequency matters as much as size: the more often an animation runs, the shorter it should be.

      Try itPlay the ladder and choose the row that feels right for opening a dropdown. Then choose one for a full-screen dialog. They should not be the same row.

      Key idea

      Duration is a function of size, distance and frequency. Small and frequent means short; large and rare can take longer.

      Pitfall

      Tuning motion by watching it once in a prototype. What feels elegant on first view feels sluggish the hundredth time, so err shorter than your first instinct.

      How it’s builtCSS 
      :root {
  --dur-instant: 100ms;  /* hover, press */
  --dur-short: 200ms;    /* toggles, chips, checkboxes */
  --dur-medium: 320ms;   /* dropdowns, tooltips, cards */
  --dur-long: 500ms;     /* modals, drawers, page panels */
}

.dropdown {
  transition: transform var(--dur-medium) cubic-bezier(0.25, 1, 0.5, 1);
}
      1.2

      Distance changes the clock

      A fixed duration makes short moves crawl and long moves rush. Scale time with distance so the perceived speed stays consistent.

      Speed is distance divided by time. If every animation lasts 400ms, a 60px nudge moves at 150px/s while a 600px slide moves at 1,500px/s: ten times faster. The eye reads that as two different objects with two different personalities.

      Scaling duration linearly overcorrects, because long moves become tediously slow. The usual compromise is the square root: doubling the distance adds about 40% more time. Clamp both ends so tiny moves are never shorter than they can be perceived and long ones never drag.

      duration = clamp(160ms, 260ms × √(distance / 100px), 700ms)

      Try itPress Play and read the speeds under each rail. On the left they differ by a factor of five; on the right they stay within a comfortable range.

      Key idea

      Keep perceived speed constant, not duration. The square root of distance is a good default; always clamp both ends.

      Pitfall

      One global transition duration for everything, including panels that travel across the whole viewport on desktop but only a few centimetres on a phone.

      How it’s builtJS 
      function scaledDuration(distance, base = 260, reference = 100) {
  const ms = base * Math.sqrt(Math.abs(distance) / reference);
  return Math.min(700, Math.max(160, ms));
}

const dx = target.x - current.x;
el.animate(
  [{ transform: 'translateX(0)' }, { transform: `translateX(${dx}px)` }],
  { duration: scaledDuration(dx), easing: 'cubic-bezier(0.2, 0, 0, 1)', fill: 'forwards' },
);
      1.3

      Enter gently, leave quickly

      Arrivals deserve a moment of grace. Departures should get out of the way.

      When something appears, the user is waiting for it. A decelerating entrance (ease-out) lands softly, and the content becomes readable as it settles. When something leaves, the user has already moved on. An accelerating exit (ease-in) that is 30–40% shorter clears the stage without competing for attention.

      Symmetric timing makes the dismissal feel like a second, unwanted animation. In CSS it is also the default: one transition rule on the element covers both directions. Put the entrance timing on the open state and the exit timing on the base rule, because the transition that applies is the one on the state you are moving to.

      Try itOpen and close both sheets a few times. Watch the closing: on the left it lingers, on the right it is simply gone.

      Key idea

      Exit duration ≈ two thirds of the entrance. Entrances decelerate (ease-out); exits accelerate (ease-in).

      Pitfall

      A single transition on the base rule. It silently gives the exit the same slow, decelerating curve as the entrance.

      How it’s builtCSS 
      .sheet {
  transform: translateY(100%);
  /* Closing: short and accelerating (applies when leaving .is-open) */
  transition: transform 200ms cubic-bezier(0.3, 0, 0.8, 0.15);
}

.sheet.is-open {
  transform: none;
  /* Opening: longer and decelerating (applies when entering .is-open) */
  transition: transform 340ms cubic-bezier(0.05, 0.7, 0.1, 1);
}
      1.4

      Feedback has a deadline

      Users forgive slow work. They do not forgive silence. Acknowledge every input within 100ms, even if the result takes longer.

      Classic response-time research (Card, Robertson and Mackinlay, popularised by Jakob Nielsen) describes three limits: about 0.1s feels instantaneous, about 1s keeps the user’s flow of thought, and about 10s is the limit of attention.

      Network requests often cannot meet the first limit, but visual feedback always can: a pressed state, a spinner, a disabled button. That acknowledgement is what makes a 600ms save feel responsive, and it prevents the double submissions that happen when a button appears to do nothing.

      Try itSet the delay to around 600ms and turn acknowledgement off, then press and press again. Watch the extra-click counter. Turn acknowledgement back on: the work takes exactly as long, but it no longer feels broken.

      Key idea

      Separate acknowledgement (always under 100ms) from completion (whenever the work is done). Motion bridges the gap between the two.

      Pitfall

      Waiting for the server before showing any pressed or loading state. Users click again, and now you have two orders, two messages or two payments.

      How it’s builtJS 
      button.addEventListener('click', async () => {
  if (button.dataset.busy) return;          // ignore repeat clicks
  button.dataset.busy = 'true';
  button.classList.add('is-busy');          // under 100ms: acknowledge
  try {
    await save();                           // however long it takes
    button.classList.add('is-done');        // then confirm
  } finally {
    button.classList.remove('is-busy');
    delete button.dataset.busy;
  }
});
      1.5

      Frames make the motion

      Smoothness is sampling. The same curve drawn sixty times a second looks like motion; drawn eight times a second it looks like a slideshow.

      Displays refresh 60 times a second, and 120 or more on many phones and laptops. That gives each frame a budget of 16.7ms (or 8.3ms at 120Hz) for your JavaScript, style recalculation, layout, paint and compositing. Miss the deadline and the browser drops a frame: the object freezes for a beat, then jumps.

      Drops are most visible during slow, steady movement, such as the long tail of an ease-out, because the eye can track the object precisely. That is why jank tends to show up at the end of an animation rather than in the middle of a fast flick.

      Try itCompare the 60fps and 30fps rows. The 30fps row looks acceptable on its own until you see them together. Now watch the slow ends of each swing, where stepping is easiest to see.

      Key idea

      The budget is 16.7ms per frame at 60Hz. Animate transform and opacity so most frames skip layout and paint entirely (chapter 09 shows why).

      Pitfall

      Driving animation with setTimeout or setInterval. Timers drift, ignore the display’s refresh and keep running in background tabs. Use requestAnimationFrame, CSS or the Web Animations API.

      How it’s builtJS 
      let last = performance.now();
let x = 0;
const velocity = 240; // px per second

function frame(now) {
  const dt = Math.min((now - last) / 1000, 0.1); // seconds since the last frame
  last = now;
  x += velocity * dt;                             // frame-rate independent
  box.style.transform = `translateX(${x}px)`;
  requestAnimationFrame(frame);
}
requestAnimationFrame(frame);
      1.6

      Delay with intent

      Delay is a feature when it filters intent. A tooltip that waits 400ms ignores a pointer that is only passing through.

      Hover is ambiguous: the pointer crosses elements on its way somewhere else. A short intent delay suppresses accidental reveals. Once the user has shown intent and one tooltip is open, neighbours should respond instantly, because the user is now exploring. Keep the group “warm” for a moment after the pointer leaves, so returning does not start the wait over.

      Menus use the mirror image: a short grace period before closing, so a diagonal mouse path towards a submenu does not snap it shut.

      Try itSweep quickly across both bars. The top one flashes every tooltip; the bottom one stays calm. Then rest on one icon in the bottom bar and slide sideways: once it is warm, it glides instantly.

      Key idea

      Wait 300–500ms before opening, respond instantly while warm, and allow a 100–300ms grace before closing.

      Pitfall

      Adding delay everywhere. On clicks, key presses and primary actions, delay reads as lag. Keyboard focus is explicit intent, so show focus tooltips immediately.

      How it’s builtJS 
      let warmUntil = 0;
let openTimer;
let closeTimer;

function onEnter(item) {
  clearTimeout(openTimer);
  clearTimeout(closeTimer);            // cancel the previous item's pending close
  const warm = tooltipIsOpen() || performance.now() < warmUntil;
  if (warm) showTooltip(item);         // instant while warm
  else openTimer = setTimeout(() => showTooltip(item), 400);
}

function onLeave() {
  clearTimeout(openTimer);
  clearTimeout(closeTimer);
  if (tooltipIsOpen()) warmUntil = performance.now() + 300;
  closeTimer = setTimeout(hideTooltip, 140); // grace period for diagonal paths
}
      Chapter recap

      What to remember

      1. Duration scales with size, distance and frequency. Small, frequent interactions: 100–250ms. Large, rare ones: up to about 500ms.
      2. Keep perceived speed constant. Scale duration with the square root of distance and clamp both ends.
      3. Enter decelerating, exit accelerating. Exits run about two thirds as long as entrances.
      4. Acknowledge every input within 100ms, even when the result takes seconds.
      5. Budget 16.7ms per frame and drive motion with requestAnimationFrame, CSS or WAAPI, never timers.
      6. Use delay to filter intent, then respond instantly once the user is engaged.
      Check yourself0/ 3

      A checkbox animation runs every time someone ticks an item in a long list. Which duration fits best?

      Small, frequent interactions want short durations. At 40ms the change is too brief to register as motion, and 600ms becomes tedious by the tenth tick.

      Two panels animate with the same fixed duration: one moves 60px, the other 900px. What happens?

      Speed is distance over time. With a fixed duration the long panel moves fifteen times faster. Scale duration with the square root of distance instead.

      A save request takes 700ms. What should the button do the moment it is clicked?

      Acknowledgement must be immediate even when completion is not. A loading state also prevents repeat clicks from submitting twice.
